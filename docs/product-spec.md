# Product and release acceptance

Status: pre-product engineering validation, 2026-10-08. Repository initially empty; this document preserves the authorized scope.

Self-hosted VM product for external AI agents. V1 hosts Apple Silicon Macs and MUST ship macOS ARM, Linux ARM, and Windows ARM guests. Concurrent independent VM processes; management-window closure must not terminate guests or remote sessions. Native AppKit/SwiftUI console using direct backend display is primary. Ordinary games and CAD require measured hardware-accelerated 3D; anti-cheat, special hardware drivers, x86 OS guests, nested virtualization and shared-kernel containers are out of scope. Windows ARM x86/x64 app translation must be measured separately. No embedded agent/model/harness.

Local stdio and authenticated remote Streamable HTTP MCP: lifecycle, screenshots with frame/time/coordinates, displays and window/accessibility metadata where available, Unicode/layout/Retina-correct input, command execution, applications, bounded/cancellable file transfer, control leases and immediate human takeover. Explicit observe/input/execute/files/lifecycle scopes; destructive actions require separate authorization. Unsupported features must fail explicitly.

Browser controls the same console over the internet: hardware H.265/HEVC capture/encode when the target browser actually supports it over WebRTC, with hardware H.264 fallback → WebRTC, latest-frame bounded queues, adaptation, idle reduction, concurrent encoder/resource budgets, window-independent capture, disconnect/reconnect/sleep behavior. Prefer direct ICE, optional Cloudflare TURN with short-lived credentials. Separately design identity, discovery, signaling, STUN, TURN and authorization. Bind device keys, allow revocation/re-pairing, authenticate media fingerprints and encrypt all sensitive control/clipboard/file/MCP data end-to-end; TLS or WebRTC alone is insufficient. Guest data stays on the user's Mac; no default cloud persistence of disks, recordings, file bodies or MCP bodies. Sensitive diagnostic collection off by default.

Swift backend and native UI; Rust platform-neutral control/image/security/MCP/session service; TypeScript browser; guest-specific integrations. Explicit backend capability queries, no assumed GPU/snapshot/balloon parity. Base images and isolated writable layers. Linux/Windows host interfaces only, no premature implementation.

Release gates: real installation/boot/shutdown/service connection for all three OSs; actual guest API/driver/GPU evidence (especially Windows D3D11/12); native copy/blocking/software-rendering analysis; headless remote; concurrent stability; fault/network/disk/sleep/upgrade recovery; security and packaging review. Windows GPU route decision precedes major graphics investment. Public release, purchases, third-party communications, protected-branch pushes and destructive actions are not authorized.

Performance: seek to exceed Parallels only in agreed, reproducible measured workloads. M1 Pro 16GB suggested host; macOS8GB + Windows8GB + Linux6GB is an overcommitted hypothesis, not admission policy. Start local1440p60 and remote1080p60; record matching hardware/versions/resources/resolution, frame-time distributions/stalls/input latency/CPU/physical memory, sample count and limitations. Separate ARM native/x86 translated, local/remote, direct/TURN and network conditions. Boot success and tests are not performance wins.

Codec requirement clarified by user on2026-10-08: prefer H.265 only when host hardware encoding and the target browser's WebRTC receive/negotiation capability intersect. Keep H.264 available; unsupported HEVC, negotiation failure or decode startup failure must trigger a bounded H.264 retry. Re-evaluate on reconnect. HTML video/MP4 HEVC playback alone does not establish WebRTC support. Record the actually received codec and fallback reason; never silently use software encoding to satisfy hardware requirements.
