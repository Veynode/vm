# Motion, copy and accessibility

Part of the [Veynode design system](../DESIGN.md). Motion and feedback, copy and i18n, accessibility, acceptance and enforcement, references (sections 10–13).

## 10. Motion and feedback

Motion has one job: to show what just happened. Things grow from where they come from (a Bot's message from its lower left, yours from the lower right, a menu from its trigger, a toast from the bottom, the details pane from the right). Keep it short, stable and interruptible, and follow the [BoardUI motion contract](boardui.md#boardui-contract).

**A one-shot motion ends within 200ms** (the avatar's greeting is the one exception, 480ms), counting any delay or stagger: a transition, an entrance or exit, a hover or press gesture, a morph. A staggered group is compressed so the last member ends by 200ms. Only loops that show a state (spinners, breathing, shimmer, the working avatar) run longer, and waits that are not motion (a tooltip's open delay, a loader's reveal delay, a toast's lifetime, a copied tick) are not counted.

Tokens (boardui-theme.css): durations `--motion-fast` 100ms (press, hover), `--motion-base` 160ms (appear, switch), `--motion-slow` 200ms (panes, progress; the ceiling), `--motion-exit` 120ms (leaving is faster than arriving); curves `ease-standard` `cubic-bezier(.2,0,0,1)` for most movement, `ease-pop` `cubic-bezier(.3,1.4,.5,1)` (a small bounce, the avatar's) for what newly appears, `ease-exit` `cubic-bezier(.4,0,1,1)` for what leaves. Every exit takes `--motion-exit` (120ms: dialog, Jump to latest, toast, tooltip), menus keeping 100ms as the fast exit.

A Bot's state shows only in its avatar's face, in lists as well: no separate spinners or badges; the only corner mark is an ink unread dot. Only what newly happens moves: history, remounts and switching conversations never replay an entrance.

Place `DialogPresence` outside conditional owners. All close paths share the lifecycle without call-site timers. Keep focus and scroll lock through exit; stale callbacks must not close a rapidly reopened surface. The right sidebar retains its existing animation owner; the dialog size-animation rule is not a reason to rewrite it. Do not animate full transcript-row dimensions with CSS; a card's answer area folding is inner content, and the row follows it through measurement.

## 11. Copy and internationalization

Use concise, specific, calm copy. Action labels such as Save changes, Reconnect, and Done, carry on are clearer than a generic OK with several meanings. Errors explain what happened and the next available step while preserving uncertainty.

### No needless words

Every word on screen, and every line a command prints, must tell the person something they need and do not already see. Before adding text, read what is shown beside it; when in doubt, leave it out. These are rules, not preferences:

- **Do not say again what a neighbour says.** A status beside a button with the same word, a description that restates its title, a hint that restates its label or the options of its select, a dialog body that repeats its title, a toast for a result already visible in the list, a placeholder that repeats the field's tip.
- **Do not narrate the interface.** No "click the button below", "choose X above", "this updates by itself", "this page reconnects by itself", "you can … later", "you can … at any time". A disabled button needs no sentence saying why when the reason is in view.
- **Do not explain mechanism.** Say the cause a person can act on and the consequence they must weigh; leave out how it works inside (which program starts which, keys, relays, retries, revisions, file paths, ports, ids).
- **No filler.** No "please", "successfully", "currently", "right now", "in order to", "for your security", 请注意, 成功地, 您可以, 目前, 暂时; no status made of two status words; no closing "try again" where a Retry control is shown. No script checks these words:
- **One sentence per decision.** A confirmation body says what is lost or stops, what is kept, and at most one further consequence; it never opens with the title again and never ends by pointing at the field or button under it. An empty state is one line and at most one button for the one next step; a second sentence goes behind an `InfoTip` ([Loading, empty and failed](components.md#loading-empty-and-failed)).
- **A hint is optional.** A row, field or heading has a tip only when the tip adds a fact. Code never builds a hint for every row.
- **Nothing takes a line of its own unless it must.** Help that matters rarely goes behind a tip mark in the row or header it belongs to; a fact that only applies in one state is shown only in that state.
- **One wording per fact.** The same state uses the same key and the same sentence everywhere it appears; a key no source uses is deleted with the code that used it. The button that runs a failed thing again is Retry (重试) everywhere, for a load, a connection, an action and a Run alike; never Try again.
- **A Bot's machine is a computer; the machine running Veynode is a node.** The Bot editor's field, Open computer, No computer and Another computer say computer; the Nodes page, a node's role and Settings say node. In Chinese 电脑 stands only where `packages/console/scripts/i18n-allowlist.json` (`zhTerminology`) lists the key; 这台机器 is the Settings page of the machine a console is served by. The action that makes a Bot is Create Bot; the one save wording in an editor is Save changes; connecting a model is Connect a model (the choice, its form and the empty workspace's button alike).
- Command output follows the same rules: one line for a result, no command reference after every start, no parenthetical internals, no ✓ line for a step that did nothing; details belong to `status` and `--json`.

### Copy budget

How long each kind of text may be; the words in it follow the rules above.

| Text                           | Budget                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| A page, dialog or column title | One line at its head's width, never cut; a name the person gave may be cut with an ellipsis |
| A button                       | A verb, up to 4 words (Save changes, Done, carry on), never Confirm or OK                   |
| A Settings row                 | A label, an optional ⓘ and one control or value                                             |
| An empty state                 | One line and at most one button                                                             |
| An error                       | What is wrong and, when it is not in view, the next step; no "try again" beside Retry       |
| An `InfoTip`                   | One or two sentences, at most 240px wide                                                    |
| A toast                        | One sentence, at most one short action                                                      |
| A confirmation                 | The question as the title; one or two sentences of what is lost                             |

### Catalogs

- Use stable semantic keys such as `t('common.settings')`; neither Chinese nor English source text is a key.
- Maintain English and Chinese copy in PO catalogs compiled by Fluenti. Interpolate complete sentences instead of concatenating a fixed word order.
- Allow English expansion and Chinese wrapping. Do not truncate approval consequences to fit a button or panel.
- Dates, times, and language use existing preferences; language choices display their native names.
- Preferences and shared UI state retain their Jotai owners; server records remain in queries. Style components do not add localStorage access or globalize transient state to unify visuals.

## 12. Accessibility and acceptance

New designs must support core keyboard operations, visible focus, correct labels, and semantic roles. Status cannot rely on color alone. Important errors/pending actions cannot exist only on hover or in brief notifications. Context actions retain a keyboard entry; new touch flows cannot depend solely on hover or right-click. The ring is the [global focus rule](foundations.md#4-color). A choice among many (the Bot avatar's head, accessory and colour pickers) is a radio group: one Tab stop, arrows, Home and End move and choose. Every `InfoTip` mark is a tab stop: focus opens its tip, Enter keeps it open, Escape closes it.

Select acceptance by changed behavior. Record the page/component, browser and dimensions where relevant, results, and unverified boundaries. Layout follows section 7. Changes to input events, send/newline behavior, or composition need actual IME verification; copy-only input changes do not. Accessibility changes need the affected screen-reader, focus, or contrast checks. State gaps in automated coverage rather than replacing verification with checked boxes.

Before delivery, review only affected areas:

- Are hierarchy and the primary action clear, with catalog primitives, tokens, and attribution?
- Do affected languages, themes, layouts, and zoom levels avoid critical clipping or overlap?
- Are keyboard behavior, focus, accessible names, and relevant reduced-motion behavior preserved?
- Do asynchronous areas cover loading, absence, failure, and submission while retaining drafts and avoiding duplicate actions?
- Do authorization, approval, and takeover displays match actual permissions?

Required commands and combinations live in the [verification matrix](https://github.com/Veynode/core/blob/main/CONTRIBUTING.md#verification-matrix); feature entry points are in [CONTRIBUTING.md](https://github.com/Veynode/core/blob/main/CONTRIBUTING.md) (`pnpm context <file>`). Select gates by changed behavior, not file location. Comments and internal renames that preserve rendered output and behavior do not trigger browser suites. Isolated copy/color changes may use the root [scoped presentation checks](https://github.com/Veynode/core/blob/main/CONTRIBUTING.md#browser-acceptance), including actual browser verification of the changed surface. Other dialog behavior or visible presentation changes require `pnpm test:browser dialogs`; other message presentation, async cards, measurement, or scrolling changes require the complete `pnpm test:browser scroll` with both fixtures. Settings surfaces run `node tests/browser/settings-design-browser.mjs`, which covers every settings page and the desktop rows across Chromium and WebKit, 390/768/1280px and both themes. Shared layout, measurement, scrolling, focus, lifecycle and theme-semantic changes retain their full gates. Translation changes also need compilation, validation, and language switching. Never weaken assertions. Reuse completed checks unless subsequent changes, failures, or unresolved concerns require a rerun.

### Enforcement

`pnpm check:design` ([scripts/check-design.mjs](https://github.com/Veynode/core/blob/main/scripts/check-design.mjs)) scans every string literal in the TypeScript of `packages/console/src`, `apps/node-web/src`, `apps/web`, `packages/machine-ui/src` and the non-vendored files under `packages/ui/src` (and reads their JSX for the element, import and inline-style rules); of stylesheets it reads only the colours (`packages/console/src/styles/*.css` and `packages/machine-ui/src`). It does not check spacing, sizes or the typography written in CSS: those rules in [Foundations](foundations.md#6-spacing-sizes-radii-elevation-and-icons) hold by review. It fails on:

Never add a file or raise a count to get a pass; migrate the class string instead. Renaming or deleting an allowlisted file requires updating the ledger. `node scripts/check-design.mjs --baseline` prints the current counts for progress tracking only. The gate also runs inside `pnpm check presentation` and `pnpm check all`.

This document does not certify existing contrast, screen-reader, or touch behavior. Documentation-only edits need path, command, and source consistency checks; historical results are not current UI acceptance.

## 13. References and maintenance

The [user-specified Apple DESIGN.md reference](https://getdesign.md/apple/design-md) is a third-party analysis of a product website. Borrow restrained hierarchy and consistency, not marketing layouts; it is not an official Apple specification.

Design principles also reference Apple HIG [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Color](https://developer.apple.com/design/human-interface-guidelines/color), [Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Typography](https://developer.apple.com/design/human-interface-guidelines/typography), and [Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai). Dimensions and implementation rules here are Veynode Web conventions; native pt values are not CSS standards.

When changing shared tokens, component roles, primitives, or key interactions, update this document, its specific contracts and the pattern catalog in the same change. New rules should solve a concrete consistency problem and give one answer. Keep entry points short and avoid duplicating the entire rule set in feature directories. Preserve the [BoardUI notice](https://github.com/Veynode/core/blob/main/packages/ui/BOARDUI-NOTICE.md), the [shadcn/ui notice](https://github.com/Veynode/core/blob/main/packages/ui/SHADCN-NOTICE.md) and its [source record](https://github.com/Veynode/core/blob/main/packages/ui/shadcn-sources.json).
