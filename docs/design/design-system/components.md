# Components

Part of the [Veynode design system](../DESIGN.md). Section 8: the shared controls and patterns, how each looks and when to use it, the states every async area has, where errors go, the pattern catalog and dialog anatomy. Their sizes come from [section 6](foundations.md#6-spacing-sizes-radii-elevation-and-icons); dialog and menu motion is the [BoardUI contract](boardui.md#boardui-contract).

## 8. Components

Start from the [pattern catalog](#pattern-catalog) and the owning feature. Use static Tailwind utilities for layout; keep CSS for third-party markup, keyframes or document behaviour (see the [style guide](https://github.com/Veynode/core/blob/main/packages/console/src/styles/README.md)). Preserve measured inline dimensions. Do not generate dynamic class names. A feature may not hand-roll a pattern that has a primitive; extend the primitive (checking its consumers) instead.

| Element                                   | The one implementation                                                                                                                                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Buttons                                   | `Button` / `ButtonLink` ([Controls](#controls))                                                                                                                                                        |
| Icon-only buttons                         | `IconButton` with `aria-label`; never a raw `<button>` with padding utilities                                                                                                                          |
| Text inputs                               | `Input` / `Textarea` inside `Field` (label above; editors, forms and Settings pages alike), never in a `SettingsRow`                                                                                   |
| Select, toggles                           | `SelectField` (`@veynode/ui/components/select-field`) with `onValueChange`, or the shadcn parts of `@veynode/ui/components/select`; `Switch`, `Checkbox`; no colour-only substitutes                   |
| A state                                   | `StateTag` ([Tags and badges](#tags-and-badges)); a generic label is a `Badge`. The computer and virtual machine state badges (`ComputerStatus`, `DiscoveredGuests`, `VmStateFact`) are `StateTag` too |
| An explanation                            | `InfoTip` beside the label it explains; never a sentence under a label and never in a head                                                                                                             |
| Anything that appears on hover to explain | [Tooltips](#tooltips)                                                                                                                                                                                  |
| Settings                                  | The shell and its rules are [Settings](settings.md): `SettingsSection`, `SettingsGroup`, `SettingsRow`, `SettingsLinkRow`, `SettingsActionRow`, `PanelHeader`                                          |
| Lists                                     | `List` + `ListRow` (+ `ListRowIcon`) ([Rows and lists](#rows-and-lists))                                                                                                                               |
| Menus                                     | `RowMenu` and `DropdownMenu` ([Menus](#menus))                                                                                                                                                         |
| Loading, nothing here, did not load       | `Skeleton*`, `EmptyState`, `PanelLoadError`, `LoadingPanel` ([Loading, empty and failed](#loading-empty-and-failed))                                                                                   |
| An error                                  | Decided by [Error placement](#error-placement): `InlineError`, `PanelLoadError`, `Notice` or a toast                                                                                                   |
| Dialogs                                   | `Modal` (or a registered shell) + `dialog-body` + `DialogFooter` ([Dialog anatomy](#dialog-anatomy)); `ConfirmDialog` before a hard-to-reverse action                                                  |

Use `Field` or `SettingsRow` to associate labels; placeholders do not replace labels. On validation failure, identify the field, preserve values and provide a reachable correction path; a red border alone is insufficient. A form says its empty required fields itself, not the browser's bubble: `useRequiredFields` (`packages/console/src/components/ui/useRequiredFields.tsx`) turns the browser's check off, marks every empty required field on submit, focuses the first and gives each an `aria-invalid` and an `InlineError`; editing a field takes its mark back. Prevent duplicate submissions and retain content while submitting. Hard-to-reverse actions need explicit objects and consequences; ordinary close, preview and reversible preferences need no confirmation dialog.

### Controls

- **Variants.** `default` for the area's main action (one per screen or dialog), `secondary` for peers, `ghost` transparent at rest, `outline` a surface with a hairline, `destructive` for what destroys. Never simulate ghost by overriding another variant's background, and never make a button stand out with colour, gradient or shadow.
- **Sizes** are the scale's ([Sizes](foundations.md#sizes)): `small` 28px in rows and label rows, `medium` 36px by default, `large` 44px for the one action of a page before the workspace and every touch target on a phone. Controls on one line share one size.
- **Touch.** On a touch screen (not `pointer-fine`) every button, inline link and tab has a 44px area to press, an invisible hit area around the drawn control; the drawn size and the row's height do not change. Neighbouring controls keep their 44px areas apart or share the line.
- **An empty date or time field** draws no date: WebKit (a phone's Safari too) shows today's date in grey, which reads as a chosen one, so `Input` leaves its native text undrawn while it is empty and not being edited (`data-empty-picker`); its label or hint says what blank means.
- **Pending** shows inside the control that started it and never moves it: the label gives way to the spinner in place (`SaveLabel`), the control disabled, its width kept. A running primary shows the spinner in place of its label (`Button` `pending`; the label stays laid out, unseen, and still names the button), never a text swap to "Saving…" or a second spinner.
- A destructive action in a dialog footer is `destructive`; in a menu it is the `danger` item (`RowMenu` draws it as `destructive`), last and apart; on a Settings page it is a `SettingsActionRow`.

### Tags and badges

- **`StateTag`** is the one state badge: its word in a 20px pill (`rounded-full`), coloured by the state: `done` green for fine, `waiting` amber for waiting on the person, `failed` red for failed, neutral for a fact (a role, a kind) and for work under way, which adds a ring. Its extra words go in its `DetailTip`, never on a new line. A row carries at most two badges.
- **One state, one colour.** The same word is the same tone everywhere (Offline is neutral in every list; red is only for failed).
- **Ground.** The neutral and working badges are `ink` 6% with `ink-2` text, so they show on a pane and in a group alike.
- A dot stands for a state only where a word does not fit: 8px for unread or new (`UnreadDot`, the sidebar tab, Jump to latest), 10px with a surface ring on a computer's icon for running (`ComputerIcon`), in the same colour as the state's badge.
- **`Badge`** is a generic label that is no state (a count, a kind beside a name); it uses the same 20px pill and the same text as `StateTag`, so the two never stand side by side in two looks.

### Rows and lists

- A list is plain divided rows, no card border around each row. A list of things is a group of `ListRow`s or `SettingsLinkRow`s: one line, 48px, its leading mark (the thing's own at 32px: a computer's icon, a logo, an avatar; or a bare 20px line icon centred in that slot, `ListRowIcon`: [Content is fields, then grouped rows](settings.md#shell)), the name, at most two badges, a value or meta at its end and at most one direct control; the rest in the row's ··· `RowMenu`, which a right click on the row opens too. A press anywhere on a row that opens something opens it; its badges and its own control stay pressable.
- Under narrow width a row keeps its 48px and its state: the meta goes first, then the name is cut (ellipsis); a badge keeps its natural width and becomes a dot, its word in the dot's `title` and for assistive technology, only where even the name at 48px does not fit beside it (`useStateFit`, `packages/ui/src/settings/state-fit.ts`). A name that is plain text carries its words as a `title`, so a cut name can be read; a sentence that would not fit one line sits behind its row's ⓘ (the Models page with no provider on a node: one `SettingsLinkRow`, "Models on this node" with the sentence behind its ⓘ). `ListRow` and `SettingsRow` keep one line on a phone too: short of room the state is cut first, then the name, and nothing moves under the row; a field or a select shrinks with the row. Only a row whose content is a sentence (`metaLines={2}`) keeps its meta under the name.
- A row's hover is `ink` 5%, its disabled state 60% opacity. A list offers a search box only from six items (`SEARCH_FROM`).

### Menus

Base UI dropdowns (`DropdownMenu`) with keyboard, focus and exit states. `RowMenu` for a row's or a page's occasional actions: icon + verb items (16px icons, `menuRowStyles`), 36px rows (44px under 600px on a touch screen), the `danger` item last and apart after a separator. Several ways to add one thing are one `RowMenu` with a labelled `trigger`. Every menu is a surface panel with `lg` corners and `shadow-float` (`MENU_POPUP` for Base UI, `MENU_POPOVER_SURFACE` for a native menu) between 200 and 260px wide (`MENU_POPOVER_WIDTH`); a hand-built popover copies none of it. Menus open with the motion in the [BoardUI contract](boardui.md#menus-and-sidebar).

### Tooltips

One look for everything that appears on hover or focus to explain: the solid tooltip surface (`TOOLTIP_SURFACE`: `surface`, ink text, `md` radius, `shadow-float`) with a 12px by 8px inset and caption text, at most 240px wide, for a button's name (`Tooltip`), an explanation (`InfoTip`) and a detail card (`DetailTip`) alike; never an ink pill, which is the toast's. The ⓘ mark is 18px with a 44px touch target. `DetailTip` takes the tooltip's motion, offset and width (`TOOLTIP_MOTION`, `TOOLTIP_OFFSET`, `TOOLTIP_MAX_WIDTH`).

### Toasts

A toast (`ToastProvider`, `toast(text, variant?, { action?, detail? })`) is the ink pill at the bottom centre (`action` fill, `on-action` text, `shadow-float`), 24px above the bottom of the window and above the home indicator (`safe-area-inset-bottom`), one at a time. It never covers a row of actions: over a dialog or page whose footer (`.modal-footer`) reaches the bottom of the window, or over a conversation's composer (`.composer-frame`), it rises to sit 12px above that row and settles back. It carries the state as a mark (done ✓, failed and waiting !, working a spinner, information none), one sentence from the catalog (reuse before adding), and at most one short text action after a hairline, sized to its text up to 420px, with no countdown bar. A timed toast has no close button: it leaves by itself (3.5s; 6s for an error or one with an action), waits while hovered or focused, and Escape sends a focused one away. A raw reason goes behind the toast's Details `DetailTip` (`detail`); such a toast stays until dismissed and keeps its close button. A failed workspace action is this toast too (`.chat-error`), never a red card, and so is a failed submit or an empty field on the sign-in pages ([Error placement](#error-placement)). An inline status card is `Alert`, a different thing from this pill: it keeps its full layout. Keep transient notifications outside virtual rows.

### Avatars

Every avatar floats within its fixed bounds; a Shape avatar also acts out the mood. Group message avatars stay 24px and never animate. The progress indicator is the Bot's character, in a Group as well, at the size the [message layout contract](message-layout.md#current-presentation) gives it.

### A state change keeps the height

Checking → checked, loading → loaded, idle → pending → done, connected → failed: a row, card, field, head or control keeps its height and position through every state it can take. Reserve every line a state can show (a second line gets placeholder text or a skeleton bar of the same line height while its value is unknown), swap a status badge in place instead of adding one, show pending inside the originating control, and put a state's extra words in its badge's `DetailTip` or `InfoTip` rather than on a new line. Only something the person asked for (opening a disclosure, adding a row) or new content arriving may change height, and then through the motion in [Motion and feedback](motion-copy-accessibility.md#10-motion-and-feedback).

### Loading, empty and failed

Every async area designs each state, in place of the content it stands for:

| State                       | User sees                                                                                         | State retained                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Initial loading             | The area itself with a bar for each unknown value (below); a registered reserve for message cards | Usable surroundings; no duplicate measurement owner              |
| Confirmed absence           | `EmptyState`: one line, and at most one button for the one next step                              | Search can clear filters without implying data must be recreated |
| Initial failure             | `PanelLoadError`: one sentence, Retry, the raw reason in a `DetailTip`                            | Input, selection and context                                     |
| Background refresh failure  | The existing data, and the failure said once                                                      | Keep content; do not call stale data current                     |
| Action submitting           | Pending in the original button or area; duplicate requests blocked                                | Button position and form content                                 |
| Success or uncertain result | Feedback matching evidence; inspection when uncertain                                             | No blind repetition of potentially completed side effects        |

- **A skeleton covers only what is not known.** A page's title, a group's heading, a row's label, a field's name and a button are known before the data is: they are drawn as themselves (the button disabled), and only the value is a bar where it will stand (`SkeletonWords` for words, `SkeletonSwitch` for a switch; a field that cannot be filled yet is the field, disabled). **Only a list whose rows are not known draws row skeletons** (`ListRowSkeleton` / `SettingsLinkRowSkeleton` in `packages/console/src/components/ui/Skeleton.tsx`, the real row so heights match by construction): the icon in the real rows' shape (`icon="plate"` round, `"logo"` a rounded square) and one bar for the name; `meta` or `status` only where every real row carries one, `sentence` where it has a line under its name, and a row's buttons keep their place undrawn. As many rows as the list had last time (`useSkeletonCount`, kept per node in `localStorage`; 3 before it ever loaded; none leaves the empty state's frame, `SkeletonEmpty`); `SettingsSectionSkeleton` only where a group's heading itself comes with the data. A list never shows a blank page while it loads.
- **One wait has one look**: a page's code arriving draws nothing (`Suspense fallback={null}`), so the page's own loading state is the only one. **The swap is in place** (`SkeletonSwap`): the blocks show only after 150ms and shimmer (still under reduced motion); when the data comes the skeleton goes at once and the content fades in where it stood over 150ms (120ms under reduced motion), never one over the other; where the content is taller or shorter, the height moves within that same motion. The one exception is a chat's transcript (owner's decision, 2026-10-22): its skeleton bubbles are the Bot's bubble colour and breathe together (opacity, 1.6s) instead of shimmering, since a sweep jumps between bubbles far apart on the two sides (2026-10-23); its messages fade in over 200ms whenever they first show, a quick load included, and once the skeleton bubbles were seen those fade out over them, holding their breath where it is, over 280ms on the exit curve, so the two are seen together, then go (`MessagesLoading leaving`). A skeleton is never cut to a height kept from another visit. A bar replaced without a swap (a value in a row, a form) fades its words in the same way in Settings and in every `Modal` (`skeleton-reveal.ts`).
- **`LoadingPanel`** (the running Bot after 600ms) only where the shape is unknown, never on a Settings page. Every Bot-loader screen (`LoadingPanel`, the workspace gates, the boot curtain, the account app's gate) is the same: the loader, 8px, one caption line in `ink-2`. `LoadingStatus` inline when pending stays inside the originating control.
- **One frame.** `EmptyState`, `PanelLoadError` and `LoadingPanel` stand centred in the same 208px frame (`min-h-52`) with a 28px icon, so one never jumps into another. `EmptyState`'s line is `text-chat-regular`; the welcome and the empty workspace keep `title-1`. A second sentence belongs in an `InfoTip`, never a description under the line; a search that found nothing is the one `NoMatches` state (`EmptyState` with `role="status"`, the wording `common.noMatches`, No matches) everywhere, with no button: the way back is the clear × inside the search field at its right end (`SearchField`, shown while the field has text); a sidebar, popover or inline list that has no room for the frame says the same words as one caption line.

### Error placement

One rule decides between an inline error and a toast: **does the failure change what the component shows?**

| Situation                                                                                                                                                     | Where the error lives                                                                                                                                                                                                  | Why                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Input invalid or rejected (name taken, URL malformed, required field)                                                                                         | `InlineError` under that control                                                                                                                                                                                       | The user must edit that exact control; the message stays until the value changes      |
| The panel's own data failed to load                                                                                                                           | `PanelLoadError` in place of the content: one sentence (`settings.loadFailed`, or the panel's own when it names what did not load) and Retry, never a red banner; the server's words, when kept, only in a `DetailTip` | Nothing else can render; a list drawn empty instead would read as nothing there       |
| A condition persists (connection lost, provider unavailable, Computer disconnected)                                                                           | `Notice` or the feature's dedicated status surface (a badge in a head or row)                                                                                                                                          | It stays true after any single action; a toast would vanish while the problem remains |
| A dialog's submit failed                                                                                                                                      | Toast, through `Modal` / `ConfirmDialog` `error` (the raw reason, `errorDetail`, behind the toast's Details); the dialog stays open as it was                                                                          | The dialog keeps its shape and what was entered; nothing is drawn in its footer       |
| A one-off action failed and the origin looks the same afterwards (approve/deny, accept plan, submit an answer, copy, delete a row, retry a run, stop a reply) | Toast                                                                                                                                                                                                                  | Nothing to fix in place; a persistent message would be stale on the next click        |
| A one-off action succeeded and the result is not visible where the user acted                                                                                 | Toast (default variant)                                                                                                                                                                                                | Confirmation only; never for results the user can already see                         |

- **A field's fault is under the field; a failed submit is a toast.** An empty or invalid field (name taken, URL malformed, required, a password too short) is an `InlineError` under that control and the message stays until the value changes. A submit that failed is a toast. The sign-in pages (`AuthPage`: the account's, the node console's) never gain a line under a field, so the page never moves: there an empty field and a failed submit are both a toast, the field at fault takes the invalid ring (`aria-invalid`) and focus, and editing it withdraws the toast (`useRequiredFields({ inline: false })`). A wrong password on sign-in is the same: a toast with the invalid ring on the field, never a line under it.
- Never show both. An action failure is a toast **or** an inline message; a run failure that is already a transcript reply is not repeated as a toast. A failure a surface shows as its state (a form's footer with the failed badge and Retry, the computer window's failed badge) is not toasted as well; only when that surface has closed before the answer comes does a toast say it, naming the reason in a few words, with the whole sentence behind Details and Retry.
- An editor's failed save (Bot, Group, Routine) keeps the draft and is said under the field it was about, or once above Save when the save failed as a whole; it never adds a line under the editor's head.
- The workspace banner stays empty while an entity editor or the computer window is open: they show the workspace's error in their own error slot, cleared when the dialog closes.
- Transcript cards (approval, plan, question, takeover) never carry inline failure text. Their actions report failure through the toast and the card stays actionable.
- An uncertain outcome is an outcome: it renders as the same quiet caption status line a failure does, never a bare sentence on a row of its own and never full-width body text. It is the one outcome that offers no one-click retry, because the work may already be done.
- A Run that failed is not an action failure: it is the reply. It renders as one of the Bot's bubbles on the Run's own row (see [Conversation and composer](interactions.md#conversation-and-composer)), never as a toast.
- An inline error clears when its cause changes (the value edits, the retry starts). A toast dismisses itself; do not park state in it. An error's words say what is wrong; where a Retry control is shown they do not add "try again".

### Pattern catalog

Every entry is a primitive in `packages/console/src/components/ui/`. `recipes.ts`, `Field`, `SettingsRow`, `SettingsSection`, `SettingsLinkRow`, `SettingsActionRow`, `Notice`, `InlineError`, `ListRow`, `StateTag`, `RowMenu`, `ProgressRing`, `SidebarHead`/`PaneHead`/`SidebarList`/`SidebarFoot`, the `SettingsPage` shell and the adapter plugin row live in `packages/ui/src/settings/` (`@veynode/ui/settings/*`) so the machine settings page (`packages/machine-ui`) looks the same; the console paths re-export them. A recipe in `recipes.ts` that nothing uses is deleted with the code that used it.

```tsx
<section className={classes("settings-page-body")} aria-label={t("nodes.title")}>
  <PanelHeader actions={<SettingsAddButton>{t("computersSettings.add")}</SettingsAddButton>} />
  <SettingsSection title={t("desktop.webAccess")} headingLevel={3}>
    <SettingsGroup footnote={t("desktop.keepRunningHelp")}>
      <SettingsRow label={t("desktop.allowBrowser")} control={<Switch checked={on} onCheckedChange={setOn} />} />
      <SettingsLinkRow label={t("computerModels.title")} value={count} onOpen={openModels} />
    </SettingsGroup>
  </SettingsSection>
</section>
<Modal title={t("roleGenerator.title")} close={close} error={error}>
  <div className={classes("dialog-body")}><Field label={t("roleGenerator.prompt")}><Textarea rows={4} /></Field></div>
  <DialogFooter>
    <Button variant="secondary" onClick={close}>{t("common.cancel")}</Button>
    <Button variant="default" onClick={generate}>{t("roleGenerator.generate")}</Button>
  </DialogFooter>
</Modal>
```

- **Settings page**: the actions in the title band (`PanelHeader`), then groups of rows, with no description on top ([Settings](settings.md)). `SettingsPage` draws the page title from its sidebar row, or from `setHeading` for a sub-page; pages never render their own `h1`, title or back arrow. That title is the page's `h2`, so a heading inside a Settings page is an `h3` (`SettingsSection headingLevel={3}`, `ListRow titleAs="h3"`, `SettingsLinkRow labelAs="h3"`); a standalone page keeps the `h2` default. A form that is a single row uses `<SettingsRow as="form" onSubmit=…>` with the submit button in `actions`. A page's Add is one `SettingsAddButton` (primary, "Add") in the title band on every page.
- **List with actions**: the content becomes a button when `onSelect` is given; actions stay outside it. Use `as="article"` with `titleAs="h3"` where browser checks or assistive users query headings; pass `data-*` hooks through props.
- **Nothing here / no results**: `EmptyState` ([Loading, empty and failed](#loading-empty-and-failed)).
- **Validation, load failure, hint**: `InlineError` under the control, `PanelLoadError` (`detail`, `busy`, `onRetry`) for a panel that did not load, `Notice` for a persistent hint.
- **Panel loading**: `LoadingPanel` centred in the space the content will fill, only where the content's shape is unknown. Never a left-aligned `<p>` beside the loader. A settings page's `Suspense` fallback draws nothing: the page's own loading state follows it.
- **Dialog with actions**: body in `dialog-body`, actions in `DialogFooter`, which stays pinned while the body scrolls. **Confirmation**: `ConfirmDialog` with a question as the title, the consequence as plain `<p>`s and the specific verb.
- **Setup page**: `/setup` (the desktop app's setup window and the page `veynode login` opens) is one page that lists what is left (`SetupPage`), not a run of steps: the app's row (logo, language) above, the title, then groups of rows that scroll, each done in place (a button gives way to a `StateTag`: Allowed, Joined, Connected). First the node's own row (name, the pencil that edits it, system, its role in an account); the account (the sign-in, create and login-code form in place for a node in none, one row naming the account for a node in one); the node's machine program, only while it is not running (Check again looks once more; a development node says it runs without it); the desktop permissions; a model, only for a node in no account (a Model row listed before the node joined an account stays without a button, no longer counted as left). What a row is for sits behind the ⓘ beside its name. The foot stays put: how many things are left on its left, and Open Veynode, which is never held back; there is no step count, Back, Continue, Later or end page. A node with nothing to ask never sees the page. A browser's new workspace with no model shows only the model card (`FirstRunSetup`). A failure to open is said in the foot, the same way on `/setup` and the first-run card. Both stand on the canvas the workspace stands on, in every state (loading and failed included), and leave the window's controls clear (`--window-controls-inset`).

| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |

| List things with actions           | `List` + `ListRow`; actions in `actions`, never inside the selectable content; a row is one line at every width, its name cut before its state |
| Show an error                      | Decide by [Error placement](#error-placement)                                                                                                  |

| Make a button stand out            | Check whether it is the area's primary action and choose the variant; never gradients, colours or shadows                                      |

| Make details usable on phones      | Check touch and keyboard access; propose a scoped entry change instead of adding exterior buttons to every message                             |

### Dialog anatomy

Dialogs are compact and quiet: header, body, footer, and only the body scrolls. Nothing else frames them: no header divider, no footer band, no icon tile. Below 600px a `Modal` (a viewer too, not a window or a full-screen one) and a preview's `ViewerOverlay` (not the full-window picture) are a sheet: as wide as the screen, on its foot, only its top corners round, clear of the home indicator or standing on the keyboard, its footer buttons sharing the row equally (`data-sheet`, `base.css`). Where a dialog stands in the window and how its header lines up with the others is the [shell](shell.md#heads).

| Part         | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Owned by                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Surface      | `rounded-xl`, `bg-surface`, `shadow-modal`, over `bg-scrim` for every shell (Modal, ViewerOverlay, the shared `Dialog`, native `<dialog>`)                                                                                                                                                                                                                                                                                                                              | `DIALOG_SURFACE`, `DIALOG_BACKDROP`           |
| Width        | `Modal size`: `sm` 400px for confirmations, `md` 480px (default) for forms and details, `lg` 640px for lists and editors, `wide` for a viewer. Never a `!` width override; a shell that needs one of these widths takes it from the `modal` recipe, never a copy                                                                                                                                                                                                        | `modal` recipe                                |
| Header       | 56px: `px-6 pt-5 pb-2`; the title is an `h2` in `text-title-2-semibold` on one line, the 28px round close button on the right. A Space page may use the compact 48px header (`Modal variant="viewer"`); the computer window's head is the same 56px row with its title in `title-3` (`variant="window"`); nothing else changes it                                                                                                                                       | `DIALOG_HEADER`                               |
| Description  | Optional and rare (an explanation belongs in an `InfoTip`), the first line of the body in `text-body-regular text-ink-2`                                                                                                                                                                                                                                                                                                                                                | `Modal description`                           |
| Body         | `px-6 pt-1`, children `gap-4`; `pb-2` above a footer, `pb-6` when it is the last thing. A registered shell's content (`DIALOG_CONTENT`) keeps the same 24px sides and foot                                                                                                                                                                                                                                                                                              | `dialog-body` recipe                          |
| Error        | A toast (`Modal` `error`), the raw reason behind its Details; the dialog keeps its height and what was entered                                                                                                                                                                                                                                                                                                                                                          | `Modal error` / `errorDetail`, `DialogFooter` |
| Footer       | `px-6 pt-3 pb-6`, `gap-2`, right-aligned, sticky under the scrolling body (pinned only while what holds it scrolls: `data-overflow`, since WebKit misplaces a sticky footer while the dialog scales in); buttons 44px tall on a narrow touch screen, unchanged in a narrow desktop window; no sentence in it; one row under 600px too, so a third button (the add-model dialog's Check connection) stays with its fields there and sits at the footer's left from 600px | `DialogFooter`                                |
| Buttons      | Left to right: an optional side action (`ghost`, `mr-auto`, e.g. Delete in an editor), Cancel (`secondary`), then the one main action (`default`, or `destructive` when it destroys). The main action names its verb, never "Confirm" or "OK"; while it runs it says so and nothing dismisses the dialog. An autosaving editor has no Cancel                                                                                                                            | `DialogFooter`, `ConfirmDialog`               |
| Confirmation | Always `ConfirmDialog` (`sm`): the title asks the question, one or two sentences say what is lost and name the object, then Cancel and the verb; no second strong action beside the verb                                                                                                                                                                                                                                                                                | `ConfirmDialog`                               |
