# Message layout contract

Part of the [Veynode design system](../DESIGN.md). Registration, measurement, state and scroll ownership, current presentation, gallery and budgets.

## Message layout contract

The transcript is a virtualized list (`packages/console/src/components/messages/VirtualMessages.tsx`) whose rows are registered, measured once and positioned directly. Every rule below exists so that no row changes height or position unexpectedly under a reader.

### Registration, loading and measurement

- Every `VirtualMessages` renderer MUST supply `getMessageLayout` using the branded `defineMessageLayout` registry (`packages/console/src/lib/message-layout-contract.ts`). New semantic content extends `MessagePart`, its estimate and `loadingHeight` policies and the data-to-layout adapter. Arbitrary estimates or generic div wrappers must not bypass registration.
- Content roots use `messagePartAttributes`; inner buttons and text need no registration. Development rejects undeclared parts and rendered counts exceeding the declared count, including attribute-only changes. Missing asynchronous parts are allowed; DOM order need not match the additive estimate order.
- `MeasuredMessage` is the only whole-row `ResizeObserver` and measurement boundary. Add no card observers, competing scroll corrections or row positioning. The documented exception is the internal long-paragraph correction in `LongMessageText`; nothing else observes content to measure rows or adjust scroll.
- Async content reserves its registered loading height, handles an initial failure with retry, and disappears only after absence is confirmed. A background refresh failure retains existing content. Estimates do not promise zero intermediate reflow.
- TanStack `directDomUpdates` alone writes row positions and spacer height. Rows are placed by `top` (`directDomUpdatesMode: "position"`), as the Group avatar rails are, not by a transform: `position: sticky` resolves against layout, which a transform does not move, and a long message's actions stick inside its row. Whole-row measurement runs before the long-paragraph correction; reversing the order can double-compensate. Do not restore `content-visibility` lazy revelation for long paragraphs.
- Markdown text parts declare their format explicitly. The estimator (`packages/console/src/lib/message-markdown-layout.ts`) reads a source's CommonMark/GFM blocks and uses Pretext for visible text, heading fonts and indentation, with separate code and table rules matching [markdown.css](https://github.com/Veynode/core/blob/main/packages/console/src/styles/markdown.css). A source without math is read by a light block scan (`packages/console/src/lib/markdown-blocks.ts`: paragraphs, headings, fenced code, lists and their looseness, quotes, tables, rules, and each block's visible words), which gives the blocks and words the full parse gives for a fraction of its cost (`packages/console/tests/unit/markdown-blocks.test.ts` holds the two equal over the study's corpus, and `message-markdown-layout.test.ts` their heights); HTML, indented code, reference links and definitions, footnotes, entities and a quote's lazy lines are parsed in full. Its syntax cache is bounded to 300 entries and 128,000 source characters; sources over 32,768 characters are not parsed and SSR uses the text fallback. DOM measurement stays authoritative for mixed inline fonts and intrinsic table sizes. Update the mixed-Markdown browser fixture when changing these styles or estimates. The constants are measured, not guessed, and every one is a whole number of pixels (`MARKDOWN` in `packages/console/src/lib/message-columns.ts`, which `packages/console/tests/unit/message-estimates.test.ts` reads against `markdown.css`; `tests/browser/height-estimate-study.mjs` reports each kind's error): a paragraph is 27px with 8px margins, a tight list item 24px (a loose one 27px, 4px from the next, as an item that ends in a nested list is), a list 24px in, a heading 16px on 24px with 13px above and 7px below, a quote 15px in, and a block that sets no margin of its own sits 10px below the one above (16px under code, a table or a quote). A table wraps its cells and is as wide as their text (`max-content`, at most 28rem a column, at least its box, the extra shared in proportion): a row is its tallest cell on 21px lines plus 10px, the header never wraps, and the box is as tall as its rows and scrolls only sideways; its borders are separate (`border-collapse: separate`), since collapsed ones are shared at half a pixel and WebKit lays a phone's table out on fractions. Inline elements (`code`, `em`, `strong`, links and the like) set `line-height: 0`, so a line is exactly the paragraph's 27px whatever face a mono or fallback glyph comes from; WebKit grew a line by a pixel or two otherwise. A code block is a 30px header over 12px of padding, 12px type on 21px lines (lines never wrap, so its height does not depend on the width) and 12px, `pre` capped at 400px (the `code` inside a `pre` takes the block's size; inline code stays 13px); a diagram is a 30px header over a 240px box; a message that is only a code block or a diagram draws no bubble padding. A displayed formula (`.katex-display`: a `$$` block, or a formula written with `\[` or `$$` anywhere in a paragraph) is a box of exactly 96px, 8px from what is above and below, the formula centred; one taller or wider is scaled down into the box (a transform, which changes no layout) when that keeps it at least 0.5 of its size, and otherwise scrolls inside it, so the estimate does not read the TeX; the words before and after one inside a paragraph are lines of their own. An inline formula is a box as tall as its line (`--formula-line`: the line height of the paragraph, item, cell or heading), set at the top of the line, so a fraction or a root may be drawn outside it but never makes the line taller. What stays an estimate is its width, which decides where the line breaks: it is KaTeX's, and the estimate counts its glyphs (`formulaGlyph`), the one error math can still make. The estimate parses with the renderer's own syntax (`packages/console/src/lib/markdown-math-syntax.ts`), so both read the same formulas. The reader's own bubble also draws a 1px border, so its words are 2px narrower and the bubble 2px taller (`BUBBLE_BORDER`; the text part says `outgoing`, and `layoutOf` takes the reader so another person's message in a Group has none). The line a message's state leaves under its bubble (a failed or held send, an undelivered message, a reply that stopped short) is 28px: 4px above, a 16px line, 8px below; a notice that stands alone is 32px. A line of image tiles is 112px, tiles per line from the column they sit in; a Run's row is 8px when its card carries Continue, otherwise the 120px reserve, except a lone failure line: its 8px, the bubble's 18px, its sentence on 23px lines beside the 20px close button (`FAILURE` in `message-columns.ts`) and, when it offers an action, 2px and one line more (a Group's Continue is counted only in a Group's transcript, and the fix a Bot's owner is shown for every reader); a card is its 18px of padding, its question on 27px lines at the card's width, then each line it draws with its margin (the exact target in mono 13px on 23px lines with 8px above, a reason on 23px lines with 4px, a receipt on 16px lines with 8px, a command in its box: 8px, 2px of border, 18px of padding and 21px a line up to the 192px it shows before the rest folds, wrapped in the width beside the `pre`'s 12px and 40px insets), its answers (a box of 18px with 36px a row, a field of 40px, a form of fields) and the 8px the status line announcing a waiting card adds (`CARD` in `message-columns.ts`, read against `card.css` by `packages/console/tests/unit/card-estimates.test.ts`; the words are said in the reader's language, so a layout carries what a card asks, not its sentence); the progress slot is a 40px line in a 54px reserve; a text is measured by Pretext block by block and the lines are added: a block is a Markdown paragraph or, for a plain message over 8,192 characters, one of the blocks of about a thousand characters it is drawn in (the browser's own cuts, so they add no error); a block over 8,192 characters is cut into pieces of at most that, at a line break (exact), else at a space, else between graphemes (a cut that is not a line break ends a line the browser would have filled on, so it adds up to one line, half a line on average; no row of the study is off by it); a Markdown reply over 32,768 characters is not parsed, its paragraphs are measured; Pretext is given a word joiner between a Latin word and the fullwidth punctuation after it, which it would otherwise start a line with. Pretext costs about 0.4ms for 1,000 characters (cold, Chromium; 40,000 characters take 5-17ms in Chromium and 5-33ms in WebKit, 80,000 take 9-28ms and 10-72ms), once for a block at a width.
- **The transcript waits for its fonts.** Widths are a function of the font: `ConversationTranscript` is not drawn (the loading state `TranscriptLoading` stands) until the body face (`--font-sans`, 15px) and the mono face (`--font-mono`, 12px) are loaded, and at most 3 seconds (`FONT_WAIT_MS` in `packages/console/src/lib/transcript-fonts.ts`); after the wait the fallback face is measured and drawn. Fonts already loaded (`document.fonts.check`) draw at once with no timer, and nothing else in the app, Settings included, waits. A face that arrives after the estimates moves them: `fontsArrived` (`packages/console/src/lib/message-layout.ts`) advances an epoch that every estimate cache is keyed by, empties Pretext's word widths and, through `observeMetrics`, makes the list estimate its unmeasured rows again. The same wait covers formulas: a conversation whose first rows have one (`mayHaveMarkdownMath`) keeps its loading state until KaTeX is loaded, 3 seconds at most (`useMathGate` in `packages/console/src/components/messages/useMathGate.ts`), because a reply is another height as the source it is written in; once it has loaded, and for a reply that arrives while the person reads, rows draw as they come.
- **Only the rows at the list's ends are estimated in full.** The last 30 rows, where a list opens, and the first 10, where older history lands (`FULL_ESTIMATE` in `packages/console/src/components/messages/VirtualMessages/estimate.ts`), go through the layout with Pretext and the Markdown parser; a row between keeps its layout's fixed parts and tells its words' height from their length (`roughHeight`: a line of the source wrapped at the width, a CJK character a square of the font's size, anything else 0.55 of it, a Markdown blank line a paragraph's margins). Such a row is measured once it is drawn, as every row is, and the anchor keeps the reader's place while it settles, so opening a chat of 200 or 900 messages costs about what one of 40 does. Which rows are full depends only on the index and the count, so it changes only when rows come or go, when the virtualizer anchors the reader's row anyway.
- **Estimate caches are bounded in entries and bytes, and hold no text.** A key is a block's length and 53-bit hash (`textKey` in `packages/console/src/lib/bounded-cache.ts`), never the text. Line counts are kept by (block hash, width, font token): the width is the width the text is laid out at (the column clamped to 450px, less the bubble's padding and, for the reader's own, its border), exact and never rounded, so a window wider than the clamp changes no key and a resize above it costs nothing; only a window or phone that narrows the column makes new keys. The caches, per mounted transcript (`VirtualMessages`; they go with it, and none grows with the conversations opened): line counts 8,192 entries and 1MiB (96 bytes and the key each, one number); prepared blocks, kept to reflow at a new width without preparing again, 600 and 16MiB (3,000 bytes and 22 a character, measured); the height of a long text for a row and width 128 and 20KiB; a Markdown syntax tree 300 entries and 128,000 source characters at 32 bytes (measured at most 8); a Markdown source's finished height at a width 2,000 and 800KB. The oldest entry goes first when either bound is reached (`packages/console/tests/unit/bounded-cache.test.ts` and the bound cases of `message-layout.test.ts` and `message-markdown-layout.test.ts`). Pretext keeps the width of every distinct word it has seen with no bound of its own (about 250 bytes a word): it is emptied after 64,000 characters have been prepared, so at most about 16MB if every character were a new word and about 1MB for prose. Measured (Chromium, heap after a forced collection, 200 messages of which 20 are 20,000-40,000 characters): the first pass adds 3.0MiB, ten more conversations through the same caches 4.9MiB in all, and dropping the transcript returns to the start. A prepared set smaller than the conversation's long blocks is read in a cycle, so it hits rarely: a width change that makes every long row new costs about 300ms for those 200 rows with a 1MiB bound, 266ms with 4MiB and 97ms with 16MiB, which is the bound kept (the owner chose it on 2026-10-16); it is `PREPARED_BYTES` in `packages/console/src/lib/message-layout.ts`.

Errors are the study's first-measure error (`tests/browser/height-estimate-study.mjs`, corpus and gallery, direct and Group, 2026-10-16, before this audit's fixes): Chromium desktop / WebKit phone. #### One-line rows

Each is a box with a fixed height, `nowrap` and an ellipsis for the part that can be long, so the estimate never reads its words. A name too long for the row is cut short and never takes a second line (a row that opens something keeps the whole name in its accessible label; the gallery's `routine-long.created` pins it).

| Row                                                                                                                             | Box                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Time separator; "From X", "To X", "Created group X", "Created routine X", "X sent a message", "X replied in Y" (`message-time`) | 8 + 20 + 4 = 32px                                                        |
| Speaker name above a Group's first bubble (`small[speaker]`)                                                                    | 16px line + 4px = 20px; beside the 24px rail                             |
| A set-aside Run's row (`aside`, `restart-aside`)                                                                                | 8px direct; 8 + the rail's 24px in a Group                               |
| Progress slot (`ReplyThinking`)                                                                                                 | 40px line in a 54px reserve (the 42px `min-h` is an open decision above) |

Lines of words whose length is the Controller's or the Bot's are measured text, not fixed boxes: a failure line, a notice under a bubble (4 + 16 + 8 = 28px, or more lines when its reason wraps) and a card's question.

Inputs that make a row not pure however its box is fixed: a face that is not loaded yet (the estimate is keyed by the font token and re-keys when it arrives), a line break at the exact width, the TeX source's width, and an image's bytes before they decode (the tile is a reserved box, so the bytes do not matter).

### State and scroll ownership

- Height-changing state MUST use `useMessageViewState` with stable per-message semantic keys. Native disclosures use `MessageDetails` or `data-message-disclosure` backed by that hook. Local-only expansion loses state on virtual unmount.
- View state belongs to `VirtualMessages` and is evicted with its message window; no unbounded global maps. Offscreen heights remain estimates or prior measurements; do not clear all caches on width changes.
- The transcript uses the native scrollbar, styled like every other scroller (thin, shown only while scrolling). Do not replace it with a drawn indicator.
- Preserve `packages/console/src/lib/scroll-anchor-policy.ts`: fully preceding rows compensate growth in both scroll directions; growth below the reading position does not drag the reader, but a row across the fold that shrinks by more than its part below the fold keeps its end in place (that much cannot all have been below the reader). Source appends follow the end only when already following. Where a scroll write stops a fling (iOS WebKit, `scrollWritesStopFling`), compensation while a touch, its fling or any scroll moves the list is held in the top padding (`TouchAnchorHold`), older history landing included: rows above the reader take it and the rows on screen stay. Once the list is still and inside its edges, the padding comes back and the held amount goes into `scrollTop` in the same task, so nothing on screen moves. The virtualizer's own deferral moved the rows on screen by every resize above them and jumped back when the fling ended (`tests/browser/message-scroll-stability.mjs`, phone case).
- **One follow band, 100px (`FOLLOW_BAND`)**: a reader resting within it, with no newer window loaded, is following and sees no Jump to latest; above it they are reading. The composer overlays the bottom of the viewport and `paddingEnd` is its height plus 16, so a reader `d` above the end has `d − 16`px of transcript under the composer and at 72 the whole progress slot is hidden; every follow therefore lands at the exact end, with the progress line fully above the composer. The virtualizer's own end anchor (`scrollEndThreshold`, 48px) is geometry, not a rule: it keeps a reader's distance through measurement and must stay below the progress slot's height. A follower is shown everything that shows up at the end: an appended message, a pending reply landing in its row, the last row growing (a card appearing in a live Run's row, a message growing in place), the progress line starting, and the composer growing under their typing. Nothing moves anybody for: the progress label changing or the line ending (the slot keeps its height), a Run finishing, history loading, a row above the fold resizing, and anything while a newer window or a focused message is in effect. A reader above the band is never pulled: their anchor row stays put. Sending always goes to the end, from wherever the person was. Virtualizer geometry may not change under a reader, so the top reserve for the load-older affordance latches for the life of the list instead of shrinking when history is exhausted.
- **The top edge is the pane's top**: the conversation header floats over it as translucent capsules and messages scroll under them. The header's band is a top inset (`--header-inset`), read once when the list mounts (from `--chat-header-band` on `.chat-main` when the header declares one, else the `.chat-header` box) and kept for the life of the list; it never animates and never follows the header's later size, so a search opening or a longer name moves no row. `paddingStart` is that inset plus the latched top reserve (the load-older affordance and history notice sit under the band at `--header-inset` + 8px); `scrollPaddingStart` is the inset, so a focused or searched message lands under the capsules, and the empty welcome starts under the band. The search panel floats over the transcript and moves nothing.
- **Arrival glide.** A reader at the end is held there by instant scroll writes that cannot themselves be animated (a short smooth follow collapses to a jump rather than chase an estimated row), so for a moment after an arrival the transcript owns the scroll position and eases it toward the live end (`packages/console/src/lib/arrival-glide.ts`), retargeting as rows are measured. While it runs it is the only writer: the virtualizer's corrections are absorbed into its live target, so no frame is painted at a position the glide then takes back. It eases by elapsed time, not by frame, so it moves the same at any refresh rate; it never moves the reader up unless the content shrank below them; every write lands before the frame is painted. Reduced motion, any wheel, touch or key from the reader, any scroll that moves them up, a focused message and a newer window all end it at once and restore the instant behaviour. None of the follows above moves the last item key, so the virtualizer's own follow never fires for them: an appended message under the persistent tail, a pending reply landing in its row, the last row growing and the progress line starting are all the transcript's own glide. Following happens once per send: acknowledging a send scrolls nothing, because the acknowledged message replaces the optimistic one in place and a second scroll would land on the estimate of the reply arriving with it and jump back when measured.
- **A message carries at most one secondary line, earned by what the reader can act on.** Under the person's own message only a failure earns it: a send that failed says why (the Controller's words) with the fix its reason implies, Resend and Edit, and no banner or toast repeats it; a message that never reached the Bot reads as the same Failed to send line with Resend and Edit, with why (its task stopped, or Veynode restarted first) in a `DetailTip` with Copy. The failed bubble stays faded; its line and actions read at full strength, actions in bold ink. A message written while the transport was down draws no line once it lands. Run states draw none (attached to the running task, handled, carried into the next task, dropped: the reader can neither act on nor correct them). Sending and confirming are silent: the send button already shows a send in flight, an unconfirmed outcome must not offer a resend that would duplicate a message the Computer may hold, and a send only waiting for its turn stays faded and draws no line, because a line removed on landing dropped everything above it at the end. A send held for the home node (`optimisticState: "held"`: written while the node does not answer, in the account web app also kept in the browser across a reload) is faded and draws no line either; it leaves when the node answers. The line ends with its action: a successful resend leaves no line. The line is registered in the layout estimate.
- **A row is placed once, at the moment it entered, and never re-placed.** A message sits at its `createdAt`; each approval is its own row at its tool call's `startedAt`; each question, sealed request or takeover is its own row at its `createdAt` (a delegated child's cards included, attributed to the child's Bot); one delivery of files (the artifacts of one tool call) is one row at the moment they arrived. The Run's own row carries only what has no moment of its own (set aside, interrupted, a failure or an uncertain outcome) and exists only once the Run has ended, at its `completedAt`. A live Run keeps a carrier row under everything it said that draws nothing and reserves nothing, so the progress slot has a Run to speak for; it is not a transcript row. Nothing sorts by a Run's status: what the Bot says later comes after a card, never over it, and a Run ending moves nothing.
- Arrival effects and working-tail following share `appendedMessageIds` (`packages/console/src/lib/message-appends.ts`): only new identities after the last retained row count as appends, after rows that were last and stayed last are set aside, because a live Run's carrier row sits under everything the Run has said and what it says next comes in ahead of it. Disjoint history or search windows do not prove an append.
- `MeasuredMessage` rebinds when a row's index changes. `workingTail` keeps pending reply keys at the end temporarily, hides their timestamps and retains the registered 56px idle tail; completion restores chronological order; source order still governs arrival effects.
- Dialog and sidebar cards are normal layout, not transcript rows. Opening details must not change row height.

### Current presentation

- **Source of the transcript.** Computer conversations render one canonical Controller projection from snapshots and ordered events. Public assistant text enters the transcript only when the Computer completes the message, under a stable `MessageId`; transport deltas stay durable for recovery but are not rendered as they arrive. Activity, tools, plans and delegations use compact disclosures, with approvals and input beside their owning Run or ToolCall. Raw reasoning, credentials and child scratch stay private. Legacy Group and Routine drafts keep their publication behaviour.
- **Seven styles and no eighth**: the time separator, a message from the person, a message from the Bot, a notice, the progress slot, the card a Bot uses to ask for something, and the takeover (that card pointing at the computer). Anything new says itself in one of these. Question, approval, takeover and a suggested plugin are one card, told apart by `data-card-kind`: the Bot's bubble with something to press, with the same fill (`bubble-bot`), 18px corner (`lg`), 8px/12px inset and body text (the question is not bolded); it joins the Bot's run of bubbles like any other (`bubbleRuns`: 4px under a bubble of the same Bot, 6px corners on the Bot's side where they meet, from the row's `data-joined-above` / `data-joined-below`) and draws no caption or status row above the question. A surface inside it (answer group, command) is a white box with a hairline edge, 8px under the text, `sm` corner. The answer group has a 4px inset; each option is a 36px row with a 6px corner and no separators, which rounds a `surface-2` plate on hover while the chevron at its end darkens and leans in 2px; a takeover's open action leads with the computer symbol in a heavier weight. A question's own field is a `surface-2` well inside that box (field ring and white fill while it has the caret) with a 28px send: an ink circle while there is something to send, a bare grey arrow while not. A code block inside a bubble takes `sm` (10px, the bubble's 18px corner less its 8px inset); a message that is only a code block or a diagram draws no second frame: the bubble is the block's surface and its own copy button goes, since the message's copy copies the code without its fences. A diagram's Diagram / Source switch is a small pill pair in the block's header; switching eases the block's height over 200ms ease-out (none under reduced motion) and the row follows through `MeasuredMessage`.
- **Measurements.** One column of 800px holds the transcript ([Columns and panes](shell.md#columns-and-panes)); in it a Bot's reply and the person's bubble read up to 450px, in a direct chat and a Group alike (the estimates in `packages/console/src/components/messages/VirtualMessages/estimate.ts` take the columns from `packages/console/src/lib/message-columns.ts`, which `packages/console/tests/unit/message-estimates.test.ts` holds to the class strings and `base.css`). A bubble and a card share the 18px corner and one inset, the speaker's run spacing is 4px within a run and 8px between rows, and a progress line, a queued wait and a notice reserve the heights the layout registers. - **Takeover card.** Its primary action opens the computer; the card is one short line and its buttons. The line says only what is in the way (`takeoverQuestion` in `packages/console/src/lib/card-question.ts`, the same sentence the computer window's bar and the conversation list show); how to do it is said in the computer window, and the buttons say how to hand back (closing the window never answers the card). A takeover in the model's own words shows those words alone. Its choices are an option list like an approval's (open the computer, Done, carry on, and on a payment I won't pay), so once handed back the option that ended it stays, checked and named for the outcome (Done, Verification passed, Not paid) and the rest fold away. A locked Mac's takeover (`screen_locked`) has no open action, because a locked screen refuses remote view and input alike; its line says the screen is locked. A Mac the person paused at the machine (⌘⇧Esc, `held_at_machine`) is the same: no open action, its line says someone at the node stopped the Bot; the Controller cannot lift that hold, so after Done, carry on the Run asks the Mac for a short while and, if the hold persists, stops trying rather than raising another card. A takeover card's Open computer opens the Bot's own desktop, ready to use. A takeover carries the screen as it was when it was asked, when the machine could give one (`screenshot`, a resource of the Computer read like a delivered file): a static picture under the question, as wide as the card and 10/16 as tall in a white hairline box, rounded down to a whole pixel so the row is pure, and the open action stays its own row under it. While the card waits, pressing the picture opens the computer as that row does; once handed back (or set aside) it stays in the record and opens whole. It carries no time. A machine held at it (`person_using`, `screen_locked`, `held_at_machine`) gives none, and a card without one is drawn as before.
- The notice a Bot-created Routine leaves (Created routine <name>) makes the name a text button when the reader can open the Routine, which opens it in the Routines list. The name is an inline element with `role="button"` (`tabIndex` 0, Enter and Space), never a `<button>`: a browser lays a `<button>` out as one unbreakable box, so a long name drops whole onto the next line and grows the notice a line taller than the plain words. The notice keeps its height either way (`tests/browser/routine-created-browser.mjs`).
- **Approval card.** A pending tool approval renders only its approval card; the run's tool call list is never expanded around it. Its question is one whole sentence in the reader's language (`approvalQuestion` in `card-question.ts`), never a recorded English phrase spliced into a translated frame. Options, least permissive first, in one list: Deny, Allow once, Allow for this task (on a hard ask a Run-long yes covers only the same kind of action, `runScopeKey`), and last Always allow <scope>, only when the Computer named a scope (`grant`). A connected tool whose name says it spends money is asked about on every call (`once`), so its card offers only Deny and Allow once. An approval is a question whose answers were written down in advance: the question card with fixed options, not a card of its own. Under the question the card says what and why, nothing more: the exact target (a command whole, or the control the Computer resolved, "“Submit” (button)") and the reason. The Bot's stated purpose is not drawn, and the card has no note field: words for the Bot go in the chat box. The reason is said from its `code` in the reader's language (`runtimeTranscript.askReason.*`) and only for a risk the Computer saw: the Bot's own ask-each-time rule (`botPolicy`) draws no reason line. The Computer's English `reason` is written for the model, so a card whose record has no code (an older Computer or journal) shows it to an English reader only and no reason line in any other language. A shell command is said for a person who has never used a terminal: the question names what it sets out to do and to what ("Allow the Bot to install ffmpeg?") from the shared dictionary in `packages/shared/src/runtime/shell-explanation.ts`, falling back to "run a command on the computer" rather than guess; the card carries no consequence line and no warning colour; the command itself is shown open or settled in the box a card's own code is shown in (`MessageCardCommand`): white, a hairline, `sm` corner, no language row, copy floating in its corner, shell highlighting that changes colour only; its lines wrap, never scrolling sideways. Past eight lines the rest folds under a fade, cut by CSS so the first frame has the box's final height; a chevron in the box's bottom corner (“Whole command”, `aria-expanded`) opens it whole and closes it again, the choice kept in the row's view state so a remount or the card settling keeps it. Other targets (a path, a host) stay one wrapping line of monospace text. The card names no deadline: it waits as a question does, and a lapse settles as "the Bot carried on without it", never as a refusal. The person's decision is on the record (`decision`): the settled card keeps that row with a check (its region's state for assistive technology is Allowed once, Allowed for this task, Always allowed or Declined) and the other rows fold away. A settled approval with no decision on the record (an older journal) says its state in the receipt line; "Closed by your message" remains only for approvals journaled before typed words stopped closing cards. Approvals preserve the original exact-call scope.
- **Suggested plugin card** (`data-card-kind="plugin"`, `suggest_plugin`). It opens on the Bot's reason, then the plugin in a white surface with a hairline (its logo or a skill or MCP symbol, name, one line of what it does, in the reader's language when the catalog has it), then Install (strong) and Not now in the answer box. Install opens Settings' install box over the workspace (`PluginInstallDialog`, outside the transcript row); the card is answered as Installed once the install commits, and what it installed is given to that Bot. Closing the install box never answers the card. Typed words never answer it; words about something else skip it. Settled, the row it was answered with stays checked (Installed, Not now) and the other folds away; skipped, expired, withdrawn, stopped and ended keep their receipt lines. Only the Bot's owner sees the buttons.
- **Payments and credentials are handovers, never cards.** A control that spends money (by its label, by what the model says the action is for, or by a press on a Mac control that reads as paying) and a field that expects a credential (a payment password among them) are never an approval: the desktop tool hands the computer to the person as a takeover (`reason` `payment` or `credential`) and the card asks them to do it there themselves. On a payment, Done, carry on says only that the person is finished at the computer, not that money moved, so the Bot is told to look at the screen before it says anything was paid; I won't pay answers with fixed words the runtimes read as nothing paid (`PAYMENT_DECLINED_ANSWER`) and the card settles as Not paid.
- **Typed words and a waiting card.** No code reads what typed words mean, in any language; the buttons are a shortcut, and whether words answer a card is the Bot's model's to recognise (`packages/shared/src/runtime/wait-contract.ts` says only which card takes what). A free-text question or a takeover takes any words as its answer, because nothing has to be recognised. Anything typed over an ordinary question or choice skips it (`skippable`; the Bot did not mark it `required`): it settles as Skipped with the line that the person wrote something else, the model is told they moved on and that their message may still answer it, and the words reach it as the Run's next input. Anything typed over a tool approval, a payment's included, or over a `required` question or choice leaves the card open with its buttons: the waiting call returns to the model, which is told the card was not denied and is still open, and the words are the Run's next input, so a person can say "use the Linux machine instead" without pressing Deny; only a card the person could have seen when they wrote is handed back. If their words answer the card, the model records it (`answer_from_person`: the card's id, the decision or option, and a quote), and the Computer accepts it only when the quote is a piece of the person's own words in a message they sent after the card was shown (never an earlier message, another speaker, a Bot, a tool result or a reply they quoted), the decision is one the card offers (a payment: once or deny; always only with a scope to remember), and the Run is one whose card they could press (not a guest's, not a Routine's); the card then settles exactly as its button would. Anything typed over a takeover is queued input: journaled as the person's message under the card, delivered once the card is answered, while the card keeps waiting and says "Your message is handed to the Bot once you answer here". A sealed card is never answered in chat: words typed over it set the Run aside and start a new request. A macOS permission card takes no typed answer either; words wait behind it. In a Group the Controller answers no card from words: they start the room's turn, which skips a waiting member's ordinary question (told on its next turn), hands an approval or a required question back to the member that waits on it, open, and that member's model may record the owner's answer the same way. Nothing closes an approval but a decision (a button, or the person's words as the model recorded them), a lapse or the Run ending.
- **Groups.** Every row a member puts in the room is attributed to them: a card is that member speaking, so an approval, question, delegation or delivered files carry the same name and rail avatar a message does, and delivered files sit in the speaker's column. "Who is asking me this?" must be answerable without opening anything. A Run whose only news was progress draws nothing, is named by nothing and reserves no height. Every reply names its member: consecutive messages from one member share a single static avatar resting at the bottom of the run (the rail follows the rows' own measurements in the frame they move, so a card folding or a row settling never leaves it behind), the member name appears once above the first bubble, and the progress line carries the member name before its action ("<name> Working"). Message avatars never animate; a direct conversation shows neither avatar nor name.
- Questions, exact-call approvals and takeover share one card and keep their distinct content; the stopped state keeps its own presentation. Queued resource waits use `ReplyThinking` with a localized waiting label and the same 40px reserve as running progress. Failed, blocked, interrupted and quota outcomes use ordinary Markdown replies with localized fallback; do not duplicate an error bubble and action card. A failure line states what happened and stops: the recovery action is the button beside it, so the sentence never also tells the reader to try again.
- **A Run set aside** keeps its open card and one way back in: a line on the card says it was set aside and why, and a question's fields stay answerable (answering continues the task, so it offers no Continue of its own). An approval, a takeover and a sealed card a restart set aside (its key went with the restart) keep Continue in the card's own actions: a strong row in its white answer box, pressed like an option, never a separate button under the card. The card never says someone else is being waited on. Two things set a Run aside this way: words typed over a sealed card, and Veynode restarting (a clean Computer shutdown) while the Run waits on a person, which leaves its card open instead of ending the task (`metadata.suspendedBy: "restart"`; the line says it was set aside when Veynode restarted). A Group member's turn and a delegated child whose parent is still at work are interrupted by a restart instead. In a direct chat with no Run under way, words typed over the free-text question of the one Run a restart set aside answer it while that Run is still the last thing that happened in the conversation (no other non-delegation Run of the Bot, a Routine's included, is live or later in the journal) and the card is within its window: the question is answered and the Computer continues. Under the same conditions, words typed over its approval or its options go to that Run: the Computer takes it up again, its own model reads them, and the card stays open until the model records the answer they give or the person answers on it. Words over a takeover, a macOS permission card, a sealed card, a Run the person set aside themselves, words sent with files, a Run something newer has followed and a card past its window start a new Run, and the card keeps its buttons and Continue. The Run's own row carries the set-aside line only when no open card is left to carry it.
- **A card collects everything it needs at once.** Signing in is an address and a password: one card with a field for each, the sealed one masked beside the plain one, one submission. A field decides for itself whether its value is sealed; a sealed value never reaches the model as text, only as a reference it can spend on a tool.
- **A card is one surface**: the question, options and answer fields sit directly on it, the options and a single field in the one white answer box, with no other panel around the answers. A single field is named by its placeholder alone and carries its submit arrow beside it. Several fields each stand as their own box under a small label and the submit is a named button beside the sealed note below them, never an arrow squeezed into the last box; a sealed box's placeholder says the Bot never receives the value, never masked dots, which read as already typed. What is being asked is the card's `h3`; the caption (Question, Approval, Your turn) is not drawn: it labels the region, and the heading carrying it and the status word is `sr-only`. A sealed card on a page without Web Crypto (a phone on plain http) shows a line saying to answer in Veynode on the computer it runs on, in place of fields it could never send. A macOS permission card asks in the reader's words from the permission it names, shows its options in the reader's language while sending the runtime's own words, and takes no typed answer; Open computer leads its rows with the computer symbol.
- **A card is written once.** The caption, the question, the exact target, the Computer's reason (a command has none on the card) and the description are rendered from the record and read the same open or settled; nothing is re-titled. A state changes only the status word beside the caption (read by assistive technology, never drawn), an instruction that shows only while open, and the answer area. A settled card keeps the open card's fill and width, so answering never reshapes it. Status words (named by `data-card-state`): Waiting for you (Your turn on a takeover), Waiting for the task owner, Set aside, Answered, Submitted securely, Allowed once / Allowed for this task / Always allowed / Declined, Expired, Withdrawn (the Run asked again in other words), Skipped (`dismissed`), Closed by your message, Done, Verification passed, Not paid (`declined`), Installed and Not now (a suggested plugin), and Stopped / Ended (a card its Run's stop or end closed before anyone answered; `ended`). One line of consequence follows wherever no checked row says what became of the card (waiting for the task owner, queued words, set aside, expired, withdrawn, skipped, stopped, ended, a sealed answer's receipt, a settled approval with no decision); an expired card names the window that passed, a day. Anything a Routine started raises no card: nobody is there to answer, so its result says what needed the person. In the answer area the picked option stays in place with a check and cannot be pressed while the others go. What goes folds away rather than vanishing (`CardFold` in `packages/console/src/components/work/HumanInputCard.tsx`): the picked row's check draws on first (160ms) and from 80ms its height and opacity fall to nothing over 120ms ease-out (200ms in all; a card that settles without a pick folds over 200ms); only a pick made in front of the reader draws (`drawn`); the rows have no separators to leave behind. Only a card the reader saw open folds: one that loads settled (history, a remount) is drawn settled at once, and under reduced motion what goes is simply gone. The fold is a change of the answer area inside the row: the row resizes through `MeasuredMessage` like any other, a reader at the end stays at the end and a reader above it is not moved. Fields go the same way. A question answered on the card, by an option or its own box, keeps the answer in the card (words typed there stay where the box stood, checked like a picked option) and draws no bubble (the Run still journals them as `<requestId>.answer`). A takeover handed back draws no bubble: its checked row says what became of it. A macOS permission answered by an option keeps it checked and draws no bubble; an older answer in words its options do not name keeps a bubble. Only words typed in the chat box that answered a card are a message the person sent, which stay a bubble under the card, and the card does not repeat them; one of the card's own options typed that way still keeps its check. A sealed answer leaves only a quiet receipt line; a takeover's primary action goes.
- **Cards never disappear.** Every card row survives every Run state: a failed Run's failure is placed as [Conversation and composer](interactions.md#conversation-and-composer) says and only the Run's own row may be dropped for it; a withdrawn card stays and says so; a delegated child's settled card stays; history windows keep cards like any other row. `HumanInputCard` drafts, choices and submission identity survive remount; text inputs remain alongside options; transient errors use `ToastProvider`; pending status stays in the originating button.
- Avatar moods that are moments, not states, never rest on screen: a finished conversation in the list sits idle rather than frozen in the done pose.
- **Progress lives in the tail slot, never in the flow**: it is always the last thing in the transcript, and a Run's own row draws nothing while the Run is live. `ReplyThinking` uses the registered 40px chrome reserve and a fixed 24px reel. Labels come from compact runtime events and follow the interface language. Expose only bounded explicit filenames and dedicated user-facing command descriptions; never derive labels from raw command text, typed inputs, full paths or outputs. Reduced motion switches immediately; remount does not replay transitions.
- **Bubble runs** (`bubbleRuns`): consecutive bubbles from one speaker read as one run, as in Messenger. A row continues the one above when both are bubbles from the same person or the same Bot and no time separator starts it; a card counts as its Bot's bubble. Files, a notice or a Run's own row that draws something break the run; a Run's carrier that draws nothing neither continues nor breaks it. A continuing row sits 4px under the one above (`chat-exchange-continued`), every other row 8px (`chat-exchange`). Bubbles have no tail. A lone bubble is rounded 18px all round (`lg`); where two bubbles of a run meet their corners on the speaker's side are 6px (`rounded-*-xs`: the first bubble's lower corner, both on a middle bubble, the last one's upper corner). The Bot's bubble is the neutral light grey `bubble-bot` with ink text, the person's the neutral dark `bubble-me`. Space sits above a row and follows from the row above only, so a message arriving never resizes one already on screen; it may tighten the lower corner of the bubble it joins, which changes a shape, not a height, and eases over 120ms (none under reduced motion).
- **Exchange view between Bots.** What two Bots said to each other leaves one notice line, "Messaged ⟨avatar⟩ Name" whichever way the words went; a stretch of lines with the same Bot, up to the person's next message or a reply with words, is one line where the last fell (`foldExchangeNotices`). It opens as `BotExchangeView` on the stretch's last words (`exchangeEnd`), which takes the chat pane's place rather than opening a dialog. Its header is the chat header: the chat's Bot, ⇄, the other Bot (which opens its own chat), and a ghost close button. Its messages are the chat's own: `ConversationTranscript` turns each notice into the message of the Bot that said it and draws them, with this Bot's answers, through the same `VirtualMessages` rows, avatar rail and speaker names as a Group; the view offers no jump to the latest. Opening, closing and going on to the other Bot are one crossfade of the whole pane (View Transitions, `packages/console/src/lib/pane-transition.ts`), held until the incoming list has settled (at most 400ms; on a touch screen only until it has rows, at most 150ms); closing returns to the chat that stayed laid out beneath, so it holds nothing. The chat stays laid out beneath the view (hidden in `app.css`), so closing it (Escape, or the chat's Bot) returns to the chat as it was.
- **Channel messages.** A message that came in through a channel (an outside service's account: the owner's own chat with the Bot, or a person in a chat of the channel) is not drawn in the transcript, and not as the person's own: it is one notice line per run, the line two Bots' messages leave ("<sender> sent a message": the arrow, the service's mark in the avatar slot, the name), a text button that opens the words (`TeamNotice` with `onOpen`). The line is the row's `notice` layout part and the rest of the run's rows draw nothing (zero-height `chrome`), so the row keeps its height whatever is said and nothing expands inline. The side, name and layout come from the row alone (`fromPerson` in the projection, built from the `origin` a stored submission carries; `parseFramed` and the id of a channel message stand in only for submissions stored before origins), so a row never draws one way and moves when a lookup arrives; only the mark waits for the channel list (`useChannelSources`: the query cache, never polled, read only when a row has an origin), and until then the avatar slot holds the sender's initial at the same size. The mark is the plugin's own `iconUrl` from the protocol (PNG, WebP or JPEG data URL), never a name list in the console. A run is one sender's consecutive rows in one account (`personSpeaker`, `bubbleRuns`): what was typed in the app, another sender, another account, a Bot's reply or a time break starts a new run, and the Bot's replies stay ordinary bubbles. Opening the line takes the chat's place with the same read-only view as two Bots' exchange (`BotExchangeView` through `swapPane`; Escape or close returns, focus goes back to the line): the sender beside this chat's Bot in the header, below it the words of that run and what the Bot answered in them up to whoever speaks next, each side named once above its run with its face on the rail, the Bot's replies drawn by the transcript's own reply path and cards left to the chat. What the person types in the app stays the right-hand bubble.
- **Mirrored channel chats.** A Bot's own direct chat also draws what happens in that Bot's chats of a channel, in time order with its private rows, as a display only. It is merged on the client (`useChannelMirrors` picks the chats, `useConversation(uid, groupId, mirrors)` reads each chat's own runtime and follows its own stream under the same query key, `mergeMirroredRows` orders by `(created, id)`), not on the Controller: the transcript is built from runtime snapshots, each chat has its own cursors, and the Controller's routes stay the one authorization (`groupAccess`). `mirrorsChannelGroups(bot, uid)` (`packages/console/src/lib/channel-mirror.ts`) is the one switch: only the Bot's owner, only chats of the owner's that a chat of the channel still sends to that Bot (`liveMirrors` from `GET /channels`; one left behind when a chat's Bot changed, or whose connection went, is history and leaves), at most `MIRROR_LIMIT` (8). Only a sender's line and the Bot's replies in words are taken (`mirrorRows`); cards, approvals, files' Runs, failures, Run rows and what the owner typed in that chat stay in it. Rows are `mirror:<groupId>:<id>` with `mirrorOf { groupId, title, service? }`, no `workId`, never stored with the direct conversation, never sent with it, never replied to, edited or continued from it (the composer sends to the direct chat alone; a mirrored reply's menu is Copy and Open ⟨chat⟩). Drawing declares nothing new: the sender's line is the same `notice` part with the chat named ("<sender> sent a message in ⟨chat⟩", its `text` for the estimate from the row alone); a mirrored reply is an ordinary direct reply (no rail avatar, no speaker name, same gutter and bubble), and only a reply with a row of another conversation above it gets one `notice` line ("<Bot> replied in ⟨chat⟩", `mirrorCaption`, `withCaption`); `bubbleSpeaker` keeps a mirrored chat's rows out of the runs of the private rows and of other chats. The notice opens the same read-only pane over that chat's rows alone, whose header leads to the chat. Not mirrored: search, unread and the sidebar preview (they stay on the direct conversation), files a Bot delivers in a chat, the owner's own typing in that chat. `tests/browser/channels-browser.ts` checks order, names, no rail avatar, the pane, the menu, the composer and a live arrival.
- **Plans and diagnostics are not drawn.** A task's plan is not drawn in the conversation: the Computer keeps it and the next Run of that task starts from it, so `update_plan` stays a tool with work to do, but what the Bot is doing is the progress slot and what it did is its reply. The gallery keeps a Run that carries a plan so the gate can prove nothing is drawn for it. Activity, diagnostics and execution checks are not drawn either and there is no Work details dialog; the Work record is read only while a takeover card needs its state.
- **Arrival motion** (`MessageArrival`) animates inner content only: a new message rises 8px and grows from .94 out of its speaker's lower corner (the Bot's bottom-left, the person's bottom-right) over 200ms on the pop curve, opaque by 60%. Initial history and remount do not replay it; under reduced motion it is only a 120ms fade. A message the person just sent rises instead from where its words sat in the composer (`lifted`, 200ms standard; the composer records the place as Send empties it, `packages/console/src/lib/send-origin.ts`, and only the bubble moves). Files delivered together pop in one after another 20ms apart, all in by 200ms. A handover notice in a group sends a small dot from the one who handed over to the one who took it (120ms, arcing 10px) and the taker pops as it lands (100ms; 200ms in all, `TeamNotice`). All of it plays only on a row `MessageArrival` marks as arriving, by transform and opacity, and never changes a row's height. Bubbles have no pseudo-element tails; the Bot's share the card's fill so a reply and the card it asks with read as one voice; outgoing bubbles keep their own colours. The progress label rolls up in place over 200ms (old words leave upwards as the new rise from below).
- **Delivered files** (`DeliveredFiles`) keep three inline previews; View all opens the shared animated dialog with all original download links and never expands the transcript list. Each file is a bubble in the Bot's fill, stacked 4px apart with the inner corners tightened: a 32px `surface` square with the file's symbol, the name giving way in the middle so its extension stays, and an `EXT · size` line. The whole bubble is the one thing to press and does the likely thing: any file downloads, a page (`.html`) opens as the page it is; the name is plain text, not a link of its own, and only a page keeps a download button beside it. Past three the last bubble is View all.
- Markdown highlighting retains literal source and identical font metrics while loading. Menu and dialog portals and tooltip and copy feedback do not change row geometry.

### Required verification

Transcript rendering, async cards, measurement or scroll changes run typecheck, the relevant unit tests and **the complete `pnpm test:browser scroll` gate** (also `pnpm test:scroll`), except isolated copy or color changes that qualify for the scoped presentation checks in [CONTRIBUTING.md](https://github.com/Veynode/core/blob/main/CONTRIBUTING.md#browser-acceptance). Shared rendering behaviour, disclosure, measurement and scrolling retain the complete gate. Extend fixtures for new height-changing content. Never relax drift assertions or suppress `ResizeObserver` loops, page errors or console errors.

The gate builds and starts its own fixtures (the synthetic performance page on port 4313 and the fixture server on 4314), cleans up what it owns, and fails on occupied ports unless they are inspected and reused with `--reuse`; for standalone scripts start them yourself and inspect existing listeners first. ### History and data budgets

[conversation-window.ts](https://github.com/Veynode/core/blob/main/packages/console/src/lib/conversation-window.ts) owns the contiguous client window: at most 300 records and an approximate 2 MiB serialized UTF-16 payload budget. Keep a single oversized message intact; this is not a browser heap limit. Paging older trims the newer end and vice versa, preserving boundary cursors. New arrivals must not displace the reader's historical window; updates to retained messages still apply.

[conversation-history.ts](https://github.com/Veynode/core/blob/main/packages/controller-core/src/conversations/conversation-history.ts) owns stable `(created, id)` pagination, change revisions and a 256 KiB response target. Preserve oversized-record progress and expired-cursor reset handling rather than truncating message bodies. Read the [window tests](https://github.com/Veynode/core/blob/main/packages/console/tests/unit/conversation-window.test.ts) and [history tests](https://github.com/Veynode/core/blob/main/tests/unit/conversation-history.test.ts) before changing these rules.

### The browser's copy (account web app)

While the home node answers, the account web app keeps a copy of what the page has seen in IndexedDB, sealed with a key this browser makes for it (`apps/web/src/offline/`, mapped in its [AGENTS.md](https://github.com/Veynode/core/blob/main/apps/web/src/offline/AGENTS.md)): the session, the workspace state (chats, Bots, Computers) and each conversation's runtime cut to its last 200 messages and the Runs behind them, at most 30 conversations, written after a pause and never in the way of drawing. A tool's result is never copied, and its input only up to 1,000 characters. [query-copy.ts](https://github.com/Veynode/core/blob/main/packages/console/src/data/query-copy.ts) decides what is copied; the host seals and stores it. A page that opens while the node does not answer draws from the copy as stale data, with the query cache paused so no read fails into an error or an empty state; when the node answers the data is read again and replaces the copy in place, through the same rows and anchors as any refresh. The copy is removed with the browser's place in the account (sign out, leave, another account, a restarted key). Loading older history is local to the rows the page holds, so it needs no connection and no switch.

Words written while the node does not answer are held in the same store, per conversation, and sent in the order written when it answers, one at a time through the composer's own send path under the same `clientMessageId`. A send with files or an answer to a card is not held: the composer keeps the draft and shows the ordinary failure, because the node holds the files and the card.
