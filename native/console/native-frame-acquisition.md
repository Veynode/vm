# Native current-frame acquisition receipt

**Version1 contract implemented and component-tested; runtime acceptance is separate and is not claimed by this document.** The [v9 exact trace](../../archive/docs-evidence/native-input-frame-race-live-v1/) proves an event can acquire an old but current picture and become ineligible in less than1ms when another presentation commits. This proposal changes native eligibility explicitly: an event proved to have acquired the current picture may finish bounded delivery after that picture is replaced. It does not renew the picture's timestamp or reinterpret diagnostic IDs as authority.

## Contract

Use a separate optional `acquisition_receipt` containing a cryptographically random128-bit, lowercase32-hex identifier. Generate it with the platform secure RNG; collision/RNG/capacity failure rejects that local event and follows existing suspension/held-state cleanup. It is neither `diagnostic_id` nor a replacement frame token. The frame remains exactly its existing eight fields; epoch and request sequence remain exact full-width u64 values. Diagnostic observation remains optional and independent.

Negotiate explicit receipt support before this native mode is enabled using the exact version1 wire below. Default legacy mode continues its existing validation and gains no receipt eligibility. Never silently fall back from an enabled receipt mode to legacy after a missing/rejected receipt. MCP, raw stale-token validation, and requests from another owner cannot mint receipts. A successful receipt says nothing about input authority or actual Guest delivery.

A receipt stores the original immutable snapshot, exact eight-field token, original callback and presentation times, source dimensions/generation, display/window/invalidation identity, original monotonic acquisition time, absolute acquisition+200ms deadline, local NativeControl connection identity/generation and activation epoch. It is eligible for issuance **only while that exact snapshot is current**, under the existing publication lock. It does not issue for a merely historical frame. The original age may exceed250ms: that is already legal for a current static picture. No field in the stored snapshot is rewritten.

Limit all outstanding receipts to34: the existing32-transition queue, one coalesced move and one in-flight request. This is a separate bounded retention of original snapshot references, not an expansion of the eight-entry presentation history. Admission at capacity is a failure, never eviction of an in-flight receipt. Prune expired records with fixed bounded work on issue/claim/validate/cancel; expiry never resets. The ring used for diagnostics remains16 and is not consulted for eligibility.

## Frozen version1 wire and ownership

- Helper capability `native_frame_acquisition_protocol:1` reports support. Explicit local opt-in is `--native-frame-acquisition`, default absent/off.
- Native attach arguments optionally carry `frame_acquisition_protocol:1` (strict JSON integer). Requested mode requires the exact echo in attach result; unsupported/missing echo fails rather than falling back. Absent request preserves the old path.
- Daemon stores that mode on the persistent native connection. TakeControl forwards it in existing `native_begin`; worker must echo it in its success ACK before daemon may publish ready, and daemon echoes it in the native TakeControl result. An older worker ignoring unknown arguments must not masquerade as support.
- Native `native_frame_acquisition_negotiated` becomes true after attach negotiation. `native_frame_acquisition_enabled` becomes true only after the complete TakeControl ready/echo chain and goes false on local suspension. Never issue a receipt before enabled.
- Mode1 native events require top-level `acquisition_receipt` (exact32 lowercase hex). Legacy events reject any such field. Existing epoch/sequence stay u64; frame stays exactly eight fields; diagnostic ID remains independent.
- `validate_displayed_frame` forwards the full optional set `acquisition_receipt`, `epoch`, `sequence`. Reject any incomplete set. Receipt success adds exact `acquisition:{version:1,epoch:u64,sequence:u64,remaining_us:1..200000}` to the existing valid/frame/current result. No receipt echo. Worker validates all four keys/types/values; no bool, float, null or extras. Legacy results containing acquisition metadata reject.
- Worker initially bounds validation/source work by `min(validation_rpc_start+200ms, authority_until)` and then shrinks to the conservative returned remaining budget as described below.

Implementation ownership: apple_backend owns native registry/Display/NativeControl/helper parsing and native tests; windows_gpu owns daemon native-control/native-input validation and broker capability/parsing/forwarding; rust_control owns qemu_native_input worker and vm-qemu QMP absolute-deadline/poison handling and their tests. No source edits across those ownership boundaries without coordination.

## Ownership and state transitions

1. **Acquire (AppKit main thread):** read ready/epoch/local generation from NativeControl under its condition, then release that condition. Under the publication lock, obtain the actual current snapshot/geometry and create an unclaimed receipt bound to that activation snapshot. Map the event against that immutable geometry. Enqueue checks ready, epoch and local generation again under the condition; if they changed, cancel the receipt and reject. This closes the activation-snapshot race without holding the publication lock while acquiring NativeControl's condition. Do not manufacture a receipt later from an arbitrary queued token.
2. **Queue owner:** each queue entry exclusively owns its receipt. Replacing a coalesced move cancels its old receipt. A transition that clears a pending move cancels it. Overflow, generation change, local queue expiry, focus loss, close, take-control cancellation, return, fatal error and EOF cancel all queued receipts. Expired entries remain rejected; no remint/rebind/replay.
3. **Claim (NativeControl transport thread):** after existing ready/generation/200ms queue checks, allocate the real next sequence and atomically bind the receipt to that exact sequence and epoch. Claim succeeds once, before writing the request, and checks original absolute deadline plus live local generation. The request includes the unchanged frame, receipt, epoch and actual sequence. Acquisition and queue-entry identity are not reconstructed from a diagnostic record. A second claim fails.
4. **Validate/consume (helper AppKit main thread):** worker first checks its existing native session/worker/display/activation epoch/sequence. It forwards the exact receipt, epoch, sequence and eight-field token to the helper. Before taking publication lock, synchronously recheck actual application-active, key-window, first-responder and NativeControl-ready state. If any fails, deactivate/cancel and suspend without calling updateInput or makeFirstResponder; do not rely only on notifications or the50ms timer. Under publication lock then receipt lock, require claimed state, exact tuple, still-live local control generation, same display/window/invalidation and source geometry/generation, and current monotonic time strictly before the original deadline. Validate against the receipt's bound original snapshot even if ordinary eight-frame history has evicted it. Consume once and return that same immutable snapshot plus `current` computed honestly against the current snapshot. A changed source/layout/window or invalidated local authority revokes the receipt; simple newer presentation alone does not. Unknown/expired/replayed/altered receipts reject and never enter the legacy path.
5. **Retire:** validation success consumes/removes the record before reply; any later I/O/QMP failure cannot reuse it. An event ACK or request error cancels an unconsumed receipt defensively. Disconnect/fatal cleanup cancels all remaining records. Repeated cancel is harmless but never means an event was delivered. The queue owner must not free the receipt before the in-flight validation has finished; immutable ownership and registry removal are separate.

All registry operations are small synchronous bounded operations. No socket I/O or AppKit dispatch occurs while holding its lock. Allowed lock nesting is publication→receipt and NativeControl-condition→receipt; registry code never acquires either outer lock. Main-thread acquisition releases NativeControl's condition before taking publication. Transport claim/cancel calls the registry directly, not dispatch_sync(main). Validation runs on main without acquiring NativeControl's condition. This avoids the existing close-window/controller-release cycle. Local cancellation can mark generation revoked immediately even when remote release is still pending; remote release semantics remain unchanged.

Source/layout/window invalidation increments its existing generation and cancels affected receipts under publication→receipt. Authority/focus/connection invalidation increments the local control generation and cancels under condition→receipt. Validation checks the registry's recorded live generation. Neither path can revive a consumed/cancelled receipt. Invalidation after a validation has already completed retains the existing cross-process limitation described below; this design does not claim a global atomic input/display transaction.

## Absolute delivery deadline through worker dispatch

The helper success reply includes `remaining_us`, the floored positive integer duration from validation to the original receipt deadline, no greater than200000. It is not a fresh200ms lease. The worker records `validation_rpc_start = Instant::now()` **before** connecting/writing that validation request, then derives a conservative local deadline:

`delivery_deadline = validation_rpc_start + remaining_us`

Do not start this budget at reply receipt. The RPC necessarily began before helper validation; using its start subtracts extra transport time and can reject early, but cannot extend the helper's original window. No cross-process clock subtraction is required. Nonpositive/out-of-range/malformed budgets reject. Worker checks the minimum of this deadline and existing2s authority deadline after validation, after source-status RPC, and at actual QMP write admission. QMP serialization/write must take this same absolute deadline, not start a fresh per-call timeout. If a write is partial, errors, or finishes beyond that boundary, treat delivery as uncertain and never replay it. In particular, a partially written JSON record poisons that QMP stream: never append synthetic release JSON to the truncated record. Preserve held-state/cleanup-unconfirmed unless a separately proven fresh-QMP cleanup path can confirm release. A complete record followed by a late ACK preserves framing, but still fails the receipt operation and requires explicit bounded release handling. The existing bounded ACK read may continue beyond the delivery deadline to preserve framing; if that ACK arrives late, worker returns validation-expired without renewing authority. It must not report normal event success. The already written event may have executed; no Guest delivery or200ms ACK-completion claim is permitted. An actual write success does not prove Guest event delivery.

The native clock is NSProcessInfo.systemUptime and the worker clock is Rust Instant. This is not a tested wall-elapsed guarantee across host sleep/wake. No sleep/wake regression has run; the planned functional acceptance is awake-only. Existing release gates remain required.

This is stricter than the present200ms local queue check: RPC/source/QMP scheduling consumes the same acquisition budget. A slow system may reject more often, which is preferable to silently extending eligibility. A local pre-QMP check alone is insufficient if a subsequent blocking write can exceed the deadline. The implementation review must inspect that write path and preserve held-state cleanup on uncertain delivery. It cannot promise zero kernel-queued bytes after an exact instant, an atomic source-status→QMP transaction, or immediate Guest execution. Existing worker/source checks and revocation remain necessary.

## Required focused verification before runtime

Use the same real production store/registry/transport paths, not duplicated policy logic:

- Old static current→new presentation in transit succeeds only with its original timely receipt; the same token without it still gets the original historical rejection. Preserve original callback age; do not change the8/250ms legacy tests.
- Claim/validation at or after200ms reject; repeated activity does not renew. A remaining budget delayed by validation/source RPC cannot restart at receipt; QMP has zero writes once its conservative deadline has expired.
- Wrong token field, epoch, sequence, connection, display, source/layout/window generation, replay and unclaimed receipt reject. Full-width epoch/sequence are not truncated to JS-safe diagnostic limits.
- Eight-frame-history eviction alone does not break a valid retained receipt; source/layout invalidation still does.34-capacity, queue overflow, move coalescing, cancellation, ACK/error/EOF and in-flight ownership release must be counted and bounded.
- Forced interleavings between acquisition/enqueue, claim/cancel, validation/invalidation and close/release demonstrate no deadlock or revival. Real Unix forwarding and QMP fixtures prove rejection performs no new input write; uncertain partial writes retain fail-closed cleanup.

Root approved this bounded implementation direction; the above wire and ownership were agreed by both Rust agents. Actual CAD verification would be a later separate run; no such pass is claimed here.
